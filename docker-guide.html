Docker — From Zero to Big Tech

Everything you will actually encounter on a real project: containers, compose, registries, CI/CD, and Kubernetes basics. Built around your Spring Boot + Oracle stack.

Why Docker?

Before Docker, the #1 complaint was "it works on my machine". A developer runs Java 17, production runs Java 11. Dev uses MySQL, prod uses Oracle. Everything breaks.

Docker solves this by packaging your application together with its entire environment — the OS libraries, runtime, config — into a single portable unit called a container.

❌ Without Docker
  • "Works on my machine"
  • Manual environment setup per dev
  • Different Java / DB versions
  • Painful onboarding (hours/days)
  • Hard to replicate bugs
✅ With Docker
  • Same container everywhere
  • docker compose up = done
  • Versions locked in image
  • Onboarding in minutes
  • Exact environment reproduced

Container vs Virtual Machine

VM Container ┌──────────────────────────┐ ┌──────────────────────────┐ │ App A │ App B │ │ App A │ App B │ ├─────────┴────────────────┤ ├─────────┴────────────────┤ │ Guest OS (full Linux) │ │ Container Runtime │ ├──────────────────────────┤ ├──────────────────────────┤ │ Hypervisor │ │ Host OS (Linux) │ ├──────────────────────────┤ ├──────────────────────────┤ │ Physical Hardware │ │ Physical Hardware │ └──────────────────────────┘ └──────────────────────────┘ Size: GBs Startup: minutes Size: MBs Startup: seconds
Key insight Containers share the host OS kernel — they are NOT full VMs. This makes them lightweight, fast to start, and cheap to run. A server that runs 5 VMs can run 50+ containers.

Core Concepts

📦
Image

A read-only blueprint. Like a Java class — it defines structure but doesn't run by itself.

🏃
Container

A running instance of an image. Like a Java object — created from a class (image).

📜
Dockerfile

A recipe to build an image. Step-by-step instructions: base OS, copy files, run commands.

🏪
Registry

A storage server for images. Docker Hub is public. Companies use private registries (ECR, GCR).

💾
Volume

Persistent storage mounted into a container. Data survives container restarts.

🌐
Network

Virtual network connecting containers. Containers talk by service name, not IP address.

The Image Layering Model

Every instruction in a Dockerfile creates a layer. Layers are cached — if nothing changed, Docker reuses the cache. This is critical for fast builds.

┌──────────────────────────────┐ ← Your app JAR (changes often) ├──────────────────────────────┤ ← COPY dependencies ├──────────────────────────────┤ ← Install Maven packages ├──────────────────────────────┤ ← Set working directory ├──────────────────────────────┤ ← Eclipse Temurin JDK 21 └──────────────────────────────┘ ← Ubuntu 22.04 base When your code changes → only the TOP layer rebuilds. Bottom layers are cached → build is fast.

Dockerfile

A Dockerfile is a plain text file with instructions to build your image.

Basic Dockerfile (Spring Boot)

# Start from an official Java 21 image
FROM eclipse-temurin:21-jdk-alpine

# Set working directory inside container
WORKDIR /app

# Copy the built JAR from your machine into the container
COPY target/day-be-0.0.1-SNAPSHOT.jar app.jar

# Tell Docker which port the app listens on (documentation only)
EXPOSE 8080

# Command that runs when the container starts
ENTRYPOINT ["java", "-jar", "app.jar"]

Common Dockerfile Instructions

InstructionPurposeExample

WORKDIRSet working directoryWORKDIR /app
COPYCopy files from host → imageCOPY pom.xml .
ADDLike COPY but also handles URLs, tarADD app.tar.gz /opt

ENVSet environment variableENV PORT=8080
ARGBuild-time variable (not in final image)ARG JAR_FILE=*.jar

Best Practice Never run your app as root inside a container. Always create a non-root user with USER. Big tech security scanners will flag root containers.

Essential Commands

Images

# Build an image from the Dockerfile in current folder
docker build -t my-app:1.0 .

# Build with a specific tag and file
docker build -t my-app:latest -f Dockerfile.prod .

# List all images
docker images

# Remove an image
docker rmi my-app:1.0

# Pull image from registry
docker pull eclipse-temurin:21-jdk-alpine

# Push image to registry
docker push myregistry.com/my-app:1.0

Containers

# Run a container (creates + starts)
docker run -d -p 8080:8080 --name my-app my-app:latest

# Flags explained:
#   -d         = detached (run in background)
#   -p 8080:8080 = host-port:container-port
#   --name     = give it a name

# List running containers
docker ps

# List all containers (including stopped)
docker ps -a

# Stop a container
docker stop my-app

# Start a stopped container
docker start my-app

# View logs
docker logs my-app
docker logs -f my-app   # follow (live stream)

# Open a shell INSIDE a running container
docker exec -it my-app bash

# Remove a container
docker rm my-app
Pro tip docker exec -it <container> bash is your best debugging tool. You can inspect files, check env vars, run commands inside the container as if you SSH'd in.

Docker Compose

Running one container is simple. But real apps have multiple services: a backend, a database, a cache, a message broker. Docker Compose manages all of them together with one file.

docker-compose.yml Structure

services:                      # define all your containers here

  app:                         # service name (also its hostname on the network)
    build: .                   # build from Dockerfile in current dir
    ports:
      - "8080:8080"            # host:container
    environment:
      - SPRING_PROFILES_ACTIVE=docker
      - DB_HOST=oracle         # refers to the 'oracle' service below by NAME
    depends_on:
      oracle:
        condition: service_healthy  # wait for oracle to be healthy first

  oracle:
    image: gvenzl/oracle-xe:21-slim
    environment:
      ORACLE_PASSWORD: ${ORACLE_PASSWORD}   # loaded from .env file
    ports:
      - "1521:1521"
    volumes:
      - oracle-data:/opt/oracle/oradata   # named volume for persistence
    healthcheck:
      test: ["CMD", "healthcheck.sh"]
      interval: 30s
      retries: 10

volumes:
  oracle-data:    # docker manages this, data survives 'docker compose down'

Key Compose Commands

docker compose up -d          # start all services in background
docker compose down           # stop and remove containers
docker compose down -v        # also delete volumes (wipe data!)
docker compose ps             # status of all services
docker compose logs -f app    # follow logs for one service
docker compose build          # rebuild images
docker compose restart app    # restart one service
docker compose exec app bash  # shell into a service

Networking

When containers are in the same Compose project, they can reach each other by service name. No IP addresses needed.

Docker Compose Network: "myapp_default" ┌─────────────────────────────────────────────────┐ │ │ │ ┌──────────────┐ ┌──────────────────┐ │ │ │ app │──────▶│ oracle │ │ │ │ :8080 │ │ :1521 │ │ │ │ │ │ │ │ │ │ DB_HOST=oracle│ │ hostname=oracle │ │ │ └──────────────┘ └──────────────────┘ │ │ │ └─────────────────────────────────────────────────┘ app connects to oracle using: jdbc:oracle:thin:@//oracle:1521/APPDB ↑ service name, not localhost!

Volumes & Data

Containers are ephemeral — when a container is deleted, all data inside is gone. Volumes solve this.

Three Ways to Persist Data

# 1. Named Volume — Docker manages the location (recommended)
volumes:
  - oracle-data:/opt/oracle/oradata

# 2. Bind Mount — maps a host directory into container (good for dev)
volumes:
  - ./init:/container-entrypoint-initdb.d  # left=host, right=container

# 3. tmpfs — in memory, wiped on stop (for sensitive temp data)
tmpfs:
  - /tmp
Rule of thumb Use named volumes for databases and persistent app data. Use bind mounts during local development to hot-reload code or seed SQL files.

Multi-Stage Builds Big Tech Pattern

In production, you do NOT want build tools (Maven, npm, Go compiler) inside your final image. They add hundreds of MB and create security risks. Multi-stage builds solve this.

Idea: use one stage to build, a second smaller stage for the final image.

# ── Stage 1: BUILD ──────────────────────────────────────
FROM eclipse-temurin:21-jdk-alpine AS builder
WORKDIR /build

# Cache dependencies first (only re-downloads when pom.xml changes)
COPY pom.xml .
RUN mvn dependency:go-offline -q

# Then copy source and build
COPY src ./src
RUN mvn package -DskipTests -q


# ── Stage 2: RUNTIME ────────────────────────────────────
FROM eclipse-temurin:21-jre-alpine   # JRE only, no compiler
WORKDIR /app

# Create non-root user (security)
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

# Copy ONLY the JAR from the build stage
COPY --from=builder /build/target/*.jar app.jar

HEALTHCHECK --interval=30s --timeout=5s \
  CMD wget -qO- http://localhost:8080/api/actuator/health || exit 1

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
Single-stage image
  • JDK + Maven + source + JAR
  • ~500 MB image
  • Maven, compiler in production
  • Larger attack surface
Multi-stage image
  • JRE + JAR only
  • ~180 MB image
  • No build tools in prod
  • Minimal attack surface

GitHub Actions Example

# .github/workflows/deploy.yml
name: Build and Deploy

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Java 21
        uses: actions/setup-java@v4
        with:
          java-version: '21'

      - name: Run tests
        run: mvn test

      - name: Build Docker image
        run: docker build -t day-be:${{ github.sha }} .

      - name: Login to Amazon ECR
        uses: aws-actions/amazon-ecr-login@v2

      - name: Push to ECR
        run: |
          docker tag day-be:${{ github.sha }} \
            ${{ secrets.ECR_URI }}/day-be:${{ github.sha }}
          docker push ${{ secrets.ECR_URI }}/day-be:${{ github.sha }}
Image Tagging Strategy In big tech, images are tagged with the Git commit SHA (abc1234), not just latest. This means every deploy is traceable — you can always roll back to an exact commit.

Kubernetes (K8s) — What You'll Hear Big Tech

Docker runs containers on one machine. Kubernetes runs containers across hundreds of machines — automatically handling scaling, restarts, load balancing, and rolling deployments. Every big tech company uses it.

Key Kubernetes Concepts

🫛
Pod

The smallest unit. One or more containers running together. Like a single docker run.

📋
Deployment

Manages pods. Declares: "I want 3 replicas of day-be:1.0 always running."

🔌
Service

Stable network endpoint for a set of pods. Like a load balancer in front of your pods.

⚙️
ConfigMap

Stores config as key-value pairs. Injected as env vars or files into pods.

🔐
Secret

Like ConfigMap but for sensitive data (passwords, tokens). Base64 encoded.

📦
Namespace

Logical isolation. Teams use separate namespaces: dev, staging, prod.

Kubernetes Cluster ┌─────────────────────────────────────────────────────────────────┐ │ Namespace: production │ │ │ │ Deployment: day-be (replicas: 3) │ │ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ │ │ Pod 1 │ │ Pod 2 │ │ Pod 3 │ ← K8s restarts │ │ │ day-be │ │ day-be │ │ day-be │ crashed pods │ │ │ :8080 │ │ :8080 │ │ :8080 │ automatically │ │ └────┬─────┘ └────┬─────┘ └────┬─────┘ │ │ └─────────────┼─────────────┘ │ │ │ │ │ Service: day-be-svc │ │ (load balances across all 3 pods) │ │ │ │ │ Ingress / Load Balancer │ │ (public internet entry) │ └─────────────────────────────────────────────────────────────────┘

Basic K8s Deployment YAML

apiVersion: apps/v1
kind: Deployment
metadata:
  name: day-be
  namespace: production
spec:
  replicas: 3                    # run 3 copies
  selector:
    matchLabels:
      app: day-be
  template:
    spec:
      containers:
        - name: day-be
          image: 123456.dkr.ecr.ap-southeast-1.amazonaws.com/day-be:abc1234
          ports:
            - containerPort: 8080
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:           # read from K8s Secret, not hardcoded
                  name: oracle-credentials
                  key: password
          resources:
            requests:                  # minimum guaranteed resources
              cpu: "250m"
              memory: "512Mi"
            limits:                    # maximum allowed
              cpu: "1000m"
              memory: "1Gi"
          livenessProbe:             # K8s restarts if this fails
            httpGet:
              path: /api/actuator/health
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10

Secrets & Config Management Never hardcode

The biggest mistake junior devs make: putting passwords in code. This gets you fired at big tech companies (and leaks make the news).

The 12-Factor App Rule: Config in Environment

# ❌ NEVER DO THIS
spring:
  datasource:
    password: MyPassword123

# ✅ DO THIS — read from environment variable
spring:
  datasource:
    password: ${DB_PASSWORD}    # Spring reads env var DB_PASSWORD

How Secrets Flow in Production

Developer stores secret in AWS Secrets Manager / Vault

Passwords, API keys, certificates — never in Git.

CI/CD pipeline reads the secret at deploy time

GitHub Actions Secrets, GitLab CI/CD Variables, Jenkins Credentials.

Secret is injected as an environment variable into the container

The container never has a config file with the password — it reads $DB_PASSWORD.

Spring Boot reads the env var via ${DB_PASSWORD}

Application code never sees where the secret came from.

Career-ending mistake Never commit .env, application-prod.yml, or any file with real passwords to Git. Always add them to .gitignore. GitHub scans public repos for secrets automatically.

Real Project Setup (Your Stack)

Here is how your Spring Boot + Oracle project would look fully Dockerized.

Project Structure

day-be/
├── Dockerfile                  multi-stage: build → JRE-only runtime
├── docker-compose.yml          local dev: app + oracle together
├── docker-compose.prod.yml     prod overrides: image from registry, no build
├── .env                        local secrets (gitignored)
└── src/main/resources/
    ├── application.yml         base config with ${env} placeholders
    ├── application-local.yml   local-only overrides (gitignored)
    └── application-docker.yml  used when SPRING_PROFILES_ACTIVE=docker

application-docker.yml

spring:
  datasource:
    # 'oracle' = the service name in docker-compose, not localhost!
    url: jdbc:oracle:thin:@//oracle:1521/${ORACLE_DATABASE:APPDB}
    username: ${APP_USER:appuser}
    password: ${APP_USER_PASSWORD}
