How to Read an Angular Project

A practical guide using the tai-chinh-angular personal finance app as a live example. Every concept is linked to a real file you can open right now.

Foundation

The Core Mental Model

Angular splits every concern into a separate file. Your job as a reader is to follow three threads:

🗄️
Where data lives
service
→
⚡
How it moves
signal / computed
→
🖥️

💡 Key insight: In this project, MoneyContainerService holds the data, signals propagate changes, and component templates render the result. When you understand this flow, you can read any Angular file quickly.
Step 1

Start at the Boot Chain

Every Angular project has the same 4-file startup sequence. Read these first — they tell you how the app wakes up.

1
index.html → Browser loads this. Contains <app-root></app-root> — the empty shell Angular fills.
2
src/main.ts → Bootstraps Angular. Just one line: bootstrapApplication(App, appConfig)
3
src/app/app.config.ts → The service registry. Adding provideHttpClient() here makes HTTP available everywhere.
4
src/app/app.ts → The root component. Everything you see on screen lives inside this. 
// main.ts — the simplest file in the project
bootstrapApplication(App, appConfig)
// Translation: "Start the app using the App component,
// configured by appConfig."
// app.config.ts — providers = things available everywhere
export const appConfig: ApplicationConfig = {
  providers: [
    provideZoneChangeDetection({ eventCoalescing: true }),
    // provideHttpClient()  ← add this when wiring a real API
  ],
};
Step 2

Read a Component in 3 Passes

Every component has 3 files. Read them in this order every time.

Pass 1 — The .ts file (the brain)

Look for exactly 4 things in order, top to bottom:

// Example: container-card/container-card.component.ts

// 1. IMPORTS — what does this component depend on?
import { MoneyContainerService } from '../../core/services/...';
import { ModalService } from '../../core/services/...';

// 2. STATE — what mutable data does it own locally?
expanded = signal(false);          // just one piece of local state

// 3. COMPUTED — derived values (auto-update, no side effects)
typeConfig  = computed(() => CONTAINER_TYPES[this.item().type]);
totalBalance = computed(() => {
  const it = this.item();
  return (it.balance ?? 0) + (it.children ?? [])
    .reduce((s, c) => s + (c.balance ?? 0), 0);
});

// 4. ACTIONS — methods the template calls when user does something
toggle()  { this.expanded.update(v => !v); }
onEdit(e: Event) {
  e.stopPropagation();
  this.modalSvc.openEdit(this.item());  // tells service to open modal
}
⚠️ Rule: If a method doesn't mutate state or call a service, it should be a computed() instead. A method that only reads and returns is a code smell.

Pass 2 — The .html file (the mirror)

The template mirrors exactly what the .ts file exposes. Look for these patterns:

<!-- container-card/container-card.component.html -->

<!-- computed() drives the CSS class -->
<div [class]="'container-card ' + typeConfig().leftCls">

  <!-- user action → calls a method -->
  <div class="card-header" (click)="toggle()">

    <!-- signal value displayed through a pipe -->
    {{ totalBalance() | currencyVnd }}

  </div>

  <!-- signal controls what is visible -->
  @if (expanded()) {
    <div class="card-body">

      <!-- data passed DOWN to child component -->
      <app-container-detail [item]="item()" />

      <!-- loop over data -->
      @for (child of item().children; track child.id) {
        <app-child-card [item]="child" [parentId]="item().id" />
      }

    </div>
  }
</div>
Template syntaxWhat it means
{{ value() }}Display a signal's current value
[input]="expr"Pass data into a child component
(click)="method()"Call a method when user acts
@if (signal()) { }Show/hide based on signal value
@for (x of list; track x.id) { }Loop and render each item
<app-child />Renders another component here
[class.active]="bool"Toggle a CSS class based on boolean
value | pipeTransform a value for display only

Pass 3 — The .scss file (appearance only)

Read this last, and only when something visual confuses you. It never affects data or behavior.

Step 3

Trace a Feature End-to-End

Pick one user action and follow it through every file it touches. This is the most powerful reading technique.

Example: user clicks "Thêm tài sản" (Add asset)

1
User clicks the button in app.html → triggers (click)="openAdd()"
2
app.ts → openAdd() { this.modalSvc.openAdd(); }
3
modal.service.ts → openAdd() { this.modal.set({ mode: 'add' }); } — signal changes
4
app.html re-renders: @if (modal()) { <app-container-modal /> } → modal appears
5
container-modal.component.ts reads the signal. effect() fires → form is populated
6
User fills form, clicks "Lưu" → container-modal.component.html triggers (click)="onSave()"
7
container-modal.component.ts calls this.containerSvc.add(payload).subscribe()
8
money-container.service.ts → this._containers.update(...) + this.persist() (saves to localStorage)
9
container-list.component.ts — filtered = computed() auto-updates → list re-renders with new item
10
modal.service.ts → this.modal.set(null) → modal disappears
📌 10 steps across 6 files. That is the complete story of one feature. Every Angular feature follows this same shape — user event → method → service signal → template re-renders.
Step 4

Use the Folder Structure as a Reading Map

src/app/
├── core/                ← READ FIRST — the data foundation
│   ├── models/          ← What shape does data take? (interfaces, types)
│   └── services/        ← Where does data live? How does it change?
│
├── shared/              ← Read when you see them used in templates
│   └── pipes/           ← Transform values for display (no logic)
│
└── features/            ← Read LAST, one component at a time
    ├── summary/          ← Simplest: reads service, shows computed values
    ├── container-list/   ← Has local filter signal, loops over service data
    ├── container-card/   ← Has local expand signal, passes data to children
    ├── child-card/       ← Same pattern as container-card, simpler
    ├── container-detail/ ← Pure display + math, no state (great to start with)
    ├── container-modal/  ← Most complex: reactive form + effect() sync
    └── confirm-dialog/   ← Simplest overlay: reads signal, calls service
📐 Rule of thumb: core/ = the foundation, read it for the data contracts. features/ = the UI, read it for behavior. Start with the simplest feature component (summary or confirm-dialog), not the most complex (container-modal).
Step 5

Recognize the 3 Recurring Patterns

Once you see these, you can read any Angular project faster because the same patterns appear everywhere.

1 Signal + Computed — reactive state 
// In the SERVICE — owns the truth
private _containers = signal<MoneyContainer[]>([]);
readonly containers = this._containers.asReadonly(); // expose read-only

// In the COMPONENT — derives from it automatically
filtered = computed(() =>
  this.svc.containers().filter(c => c.type === this.activeFilter())
);
📏 Rule: signal() = mutable source of truth. computed() = an auto-updating view of it. Never mutate a computed value — only the original signal.
2 Service as event bus — no Output chains 
// WITHOUT this pattern (bad): Output events bubble up 3 levels
// child-card → container-card → container-list → app

// WITH this pattern (used here): any component calls the service directly
// In child-card.component.ts (deep in the tree):
onEdit(e: Event) {
  e.stopPropagation();
  this.modalSvc.openEditChild(this.parentId(), this.item()); // direct call
}

// In app.ts (at the root), the signal is just read:
modal = this.modalSvc.modal;
// @if (modal()) { <app-container-modal /> }
📏 Rule: When multiple components at different depths need to communicate, a shared service with signals replaces @Output + EventEmitter chains. Look for inject(ModalService) as the sign that a component uses this pattern.
3 effect() — bridge from signal to non-signal 
// container-modal.component.ts
constructor() {
  effect(() => {
    const s = this.state(); // reads a signal → effect re-runs when it changes
    if (!s) return;

    // FormGroup is NOT a signal, so we bridge manually:
    this.form.reset({
      type:    s.item?.type    ?? 'cash',
      name:    s.item?.name    ?? '',
      balance: s.item?.balance ?? 0,
      // ...
    });
  });
}
📏 Rule: effect() runs whenever any signal it reads changes. Use it only to bridge signals → non-signal things (like a FormGroup, a chart library, or localStorage). If you find yourself writing effect() to update another signal, use computed() instead.
Deep Dive

STATE vs COMPUTED — Why Angular Created These

The problem they solve

Before signals, you had plain properties. When one changed, Angular had no idea — it had to check everything on every event. And when you had derived data (filtered lists, totals), you had to manually keep them in sync yourself:

// ❌ OLD WAY — plain properties, manual syncing
class OldContainerList {
  containers = [];        // raw data
  filter     = 'all';    // raw filter
  filtered   = [];       // you maintain this yourself — always in danger of going stale

  setFilter(f) {
    this.filter = f;
    this.filtered = this.containers.filter(c => c.type === f); // must remember
  }

  addItem(item) {
    this.containers.push(item);
    this.filtered = this.containers.filter(c => c.type === this.filter); // must remember again
    // Forget either line → UI shows wrong data. No error, just a silent bug.
  }
}
⚠️ The core bug: every time containers or filter changes, you must manually remember to update filtered. Add more derived values → more things to forget → more bugs.

signal() — a value that announces when it changes

Think of it like an Excel cell you type into. The moment you change it, everything that references it knows immediately. Angular no longer has to check everything — it knows exactly what changed.

// A signal wraps a value and makes it "watchable"
filter = signal('all');

// Read it — always call it like a function
console.log(this.filter());     // 'all'

// Set a new value — Angular is notified instantly
this.filter.set('bank');

// Update based on the current value
this.expanded.update(v => !v);  // toggle true/false

In our project, every piece of mutable state is a signal:

// money-container.service.ts — the actual data
private _containers = signal<MoneyContainer[]>([...]);

// container-list.component.ts — which filter tab is active
activeFilter = signal('all');

// container-card.component.ts — is this card expanded?
expanded = signal(false);
💡 Why not a plain variable? A plain variable changes silently. A signal change tells Angular: "something changed here, re-render anything that depends on me." Without that announcement, Angular doesn't know when to update the screen.

computed() — a formula that is always up to date

Think of it like an Excel formula cell. =A1 + B1 — you never update it manually. Whenever A1 or B1 changes, the formula recalculates itself. You declare the relationship once.

// DECLARE the relationship once — Angular handles recalculation forever
filtered = computed(() =>
  this.svc.containers().filter(c => c.type === this.activeFilter())
);

Now whenever either containers or activeFilter changes, filtered recalculates automatically. You never call a function to update it. You never forget. It is always correct.

More examples from our project:

// container-card.component.ts
// "total = my balance + sum of all children balances"
totalBalance = computed(() => {
  const it = this.item();
  return (it.balance ?? 0) +
    (it.children ?? []).reduce((sum, c) => sum + (c.balance ?? 0), 0);
});

// summary.component.ts
// "add up every container to get the 4 summary numbers"
summary = computed(() => {
  let asset = 0, loan = 0, invest = 0;
  this.svc.containers().forEach(c => {
    [c, ...(c.children ?? [])].forEach(x => {
      if (x.type === 'loan')                               loan   += Math.abs(x.balance ?? 0);
      else if (x.type === 'invest' || x.type === 'crypto') invest += (x.balance ?? 0);
      else                                                 asset  += (x.balance ?? 0);
    });
  });
  return { asset, loan, invest, net: asset + invest - loan };
});

The same problem, two ways

// ❌ OLD — you manually sync everything, every time
class OldList {
  containers = [];
  filter     = 'all';
  filtered   = [];   // duplicate state — you own the syncing

  setFilter(f) {
    this.filter = f;
    this.filtered = this.containers.filter(c => c.type === f); // easy to forget
  }
  addItem(item) {
    this.containers.push(item);
    this.filtered = this.containers.filter(c => c.type === this.filter); // easy to forget
  }
}

// ✅ NEW — declare the relationship once, Angular handles it forever
class NewList {
  containers = signal([]);
  filter     = signal('all');
  filtered   = computed(() =>                   // always correct, always in sync
    this.containers().filter(c => c.type === this.filter())
  );

  setFilter(f) { this.filter.set(f); }              // filtered auto-updates
  addItem(item) { this.containers.update(l => [...l, item]); } // filtered auto-updates
}

How they work together — follow the chain

User clicks a filter button → one signal changes → one computed updates → screen updates:

// 1. User clicks "Ngân hàng" button
this.activeFilter.set('bank')           // signal changes

// 2. filtered reacts automatically (you never call it)
filtered = computed(() =>
  this.svc.containers().filter(c => c.type === this.activeFilter())
)

// 3. Template re-renders automatically
// @for (item of filtered(); track item.id) { ... }
📌 Nothing else to do. No method calls, no manual syncing, no "remember to update X when Y changes." You declared the relationship once — Angular maintains it forever.

When to use each — the decision rule

SituationUseExample in project
Data a user action or API call changessignal()activeFilter, expanded, _containers
A value calculated from other signalscomputed()filtered, totalBalance, summary
A method that only reads signals and returns a valueConvert to computed()Any getTotal() style method
A side-effect when a signal changes (syncing a form, localStorage)effect()Form reset in container-modal
🧪 One-line test: "Does a user action or API call set this value?" → signal(). "Is this just math or filtering on top of other signals?" → computed().
